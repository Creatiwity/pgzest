# pgzest demo: from SQL to typed Rust

A small ordering application (restaurants, dishes, customers, orders),
written like a real project:

```
pgzest.toml          where the schema, migrations and queries live
schema/               the complete state of the database, hand-written (declarative)
migrations/           its history, generated by `pgzest migrate create`
macros/               fragments: SQL written once, inserted with `@name`
queries/              the named queries, one Rust module per file
sandbox/              playground: deliberate errors, queries to hover
data/dishes.csv       imported with COPY
src/queries.rs        one line: `pgzest_macros::queries!("queries");`
src/inline.rs         queries written in the code: `pgzest_macros::sql! { … }`
src/main.rs           the program that uses the generated code
```

The schema is **never read from a database**: pgzest replays `schema/` on
a rebuilt PostgreSQL 18 catalog (types, functions, operators, extensions),
and analyzes each query the way PostgreSQL would. The migrations are
replayed separately: they must lead exactly to this schema.

## Running

From the repository root:

```sh
make demo        # builds the language server and the extension, opens VS Code on the demo
make demo-run    # starts PostgreSQL 18 (Docker) and runs the Rust scenario
```

`make demo` opens a VS Code window with the pgzest extension loaded in
development mode: nothing is installed in your VS Code. For Rust
exploration (go to the definition of generated code, live `query!`
errors), install the recommended `rust-analyzer` extension.

## Guided tour

### 1. What the editor knows about a query

Open `queries/restaurants.sql` and hover the `-- name: restaurant_by_slug` line.
The hover shows the query's **descriptor**: its parameters, its columns
with their type and nullability, and its row count (`optional`, because
`slug` is `UNIQUE`). That is exactly what the Rust function becomes.

To try in `queries/`:

- `menu.sql`, `menu_of`: the columns of a view are nullable (PostgreSQL
  does not keep `NOT NULL` in a view), hence `Option`s in Rust;
- `menu.sql`, `dish_counts`: `count(*)` is non-null, `min(price)` may be
  null, the aggregate without `GROUP BY` returns exactly one row;
- `customers.sql`, `upsert_customer`: `$phone` goes into a nullable column,
  hence `Option<&str>`; the unconditional upsert always returns its row
  (`one`);
- `orders.sql`, `order_summary :optional`: the analysis infers `many`
  (there is a `GROUP BY`), the declaration narrows it to `optional`;
- `orders.sql`, `orders_of_restaurant`: `$status?` is an optional filter
  (`Option<OrderStatus>`);
- `orders.sql`, `orders_page`: pagination with variants, `[[ … ]]` filters
  and `{{ … }}` sort order; hover the header, then `$status`. All eight
  variants are checked; break one (`o.statut` in a block) to see the
  error, with the variant as a hint.

### 2. The type of what is under the cursor

In `sandbox/2-explore.sql`, hover `c.email` (a `citext`, nullable because
of the `LEFT JOIN`), `o.status` (the `order_status` enum), `order_total`
(the SQL function from the migration)… The hover comes from the analysis
of the whole query: the same name (`id`) has the type of the table it
refers to where it stands.

### 3. Errors, as PostgreSQL would report them

`sandbox/1-errors.sql` contains ten faulty queries, underlined in red.
Fix them one by one to watch the diagnostic disappear:

- incompatible types (`text = integer`, an enum compared with an integer);
- unknown column or table, ambiguous column;
- explicit value in a `GENERATED ALWAYS` column;
- `DEFAULT` outside an `INSERT … VALUES` or a `SET`;
- a parameter whose type nothing fixes, a contradicted declared
  cardinality;
- a query claiming to return a dish's card (`-> dish_card`) without having
  its columns.

Same verdict in the CLI: `../../target/debug/pgzest check sandbox/*.sql`.

### 4. Writing a projection only once

`macros/projections.sql` declares **fragments**: `dish_card(d)`, a dish's
card, and `affordable(d)`, a predicate. In `queries/menu.sql`, hover
`@dish_card(d)`: the editor shows its documentation and the inserted SQL
(`d.id, d.name, …`). `@affordable(d)` is inserted in parentheses, so that
the surrounding `AND` does not split it.

`vegetarian_dishes` (same file) declares `-> dish_card`, and
`affordable_dishes` (`queries/promotions/deals.sql`, another module)
`-> menu::dish_card`: their rows have the shape of `dish_card`'s, checked
column by column, and the Rust code has a single struct,
`queries::menu::DishCardRow`, for all three queries.

Add `d.tags` to the fragment, without touching anything else: the three
queries change together, and `DishCardRow` gains a field.

### 5. The declarative schema, generated migrations

`schema/` describes the database as it should be: the complete
`CREATE TABLE`s, the functions, the triggers, the view. Add a column to
`orders` in `schema/1-orders.sql`, **without saving**:

```sql
    tip        cents,
```

- In `sandbox/2-explore.sql`, add `o.tip` to a query: it is accepted, the
  unsaved text of the schema is authoritative.
- `migrations/0004_loyalty_traced.sql`, the latest migration, carries an
  information diagnostic: the migrations no longer lead to the schema.

Save, then:

```sh
../../target/debug/pgzest migrate create tip
```

`migrations/0005_tip.sql` is written (`ALTER TABLE orders ADD COLUMN
tip cents`), with its context header, after verification by replay (a
column declared in the middle of the table gets a note: PostgreSQL appends
it at the end); the information diagnostic disappears, and
`pgzest migrate check` (for CI) is green. Dropping a column would be
refused without `--allow-destructive`; an index created on an existing
table is flagged (writes are blocked while it is built).
`0003_menu_public.sql` was generated this way: the view only existed in
the schema.

PL/pgSQL bodies are checked too. In `schema/2-loyalty.sql`, change
`NEW.customer_id` to `NEW.client_id` in the trigger's body: the trigger is
attached to `orders`, which has no such field, and the error says so.

### 6. Tracing the routines

`schema/2-loyalty.sql` writes the loyalty trigger and the function it
calls with macros (`@trigger`, `@function`): plain SQL routines stay as
written, macro routines opt in to instrumentation. `pgzest.toml` sets the
level:

```toml
[log]
level = "step"
target = "notice"
```

Put the cursor in the `@trigger` and press **⌘⌥E**: each run records its
start, its caller, its depth and its `UPDATE` (row count, source line),
and raises them as notices. `migrations/0004_loyalty_traced.sql` was
generated from it: its header says `log=step:notice`, and the replay
checks the routines against it. Set `level = "none"` and run `pgzest
migrate check`: the migrations no longer match — the instrumentation is
part of the schema, never added behind its back.

Only the runs of a sampled trace raise them: `src/main.rs` passes a W3C
`traceparent` whose `sampled` flag is set (`trace::set_traceparent`); a
request the application does not trace pays a few microseconds per run.
It reads the notices off the connection
(`pgzest_runtime::trace::Tracing`, feature `trace`) and prints the tree
of runs the statement serving the order caused:

```
   orders_award_loyalty_fn — 0.79 ms
     · UPDATE customers (schema/2-loyalty.sql:16): 1 row(s)
       └ loyalty_points_of — 0.34 ms
```

An application hands the trees to OpenTelemetry instead
(`trace::otel::export`, feature `opentelemetry`), under the span of its
request, with the exporter it uses.

### 7. The generated Rust code

`src/queries.rs` is a single line: `pgzest_macros::queries!("queries");`.
The macro describes each query of `queries/` at compile time and generates
one module per file: `queries::menu`, `queries::orders`,
`queries::promotions::deals`… PostgreSQL enums are at the root
(`queries::DishKind`). To read the produced code:

```sh
../../target/debug/pgzest describe --rust queries/menu.sql
```

In `src/main.rs`, use "Go to Definition" on `queries::menu::add_dish`
(rust-analyzer), or hover it:
`AddDishParams { kind: DishKind, price: i32, tags: &[String], … }`.

Break a query in `queries/` (for example `restaurant_id` →
`restaurant`), then `cargo build -p pgzest-demo`: compilation fails, with
the position of the error in the SQL file. No database is contacted for
that.

`src/inline.rs` shows `sql!`: a query written in the Rust code, the string
holding only the SQL, with the name and cardinality as macro parameters.
`dishes_by_price` reuses the dish card of `queries/menu.sql`
(`-> crate::queries::menu::DishCardRow`), checked at compile time: replace
`FROM dishes d` with `FROM restaurants r LEFT JOIN dishes d ON
d.restaurant_id = r.id`, and `cargo build` refuses, column by column
("`price` may be null here…"). Edits to the string are picked up by the
editor as you type, and the string is treated like a SQL file:
highlighting, errors underlined inside the string, hover (the descriptor
on `dishes_by_price`, the type of `d.price`, the `@dish_card` fragment),
completion. Enums are generated once, in `crate::db`
(`#[pgzest_macros::types]`, `[rust] types` in pgzest.toml).

`src/lib.rs` also shows `query!`, a one-off query inside an expression,
checked the same way.

### 8. Running it

```sh
make demo-run
```

The program recreates a `pgzest_demo` database, applies the migrations to
it (like a deployment: the schema is their target, not a script), imports
the dishes with `COPY` (CSV), then runs the scenario. It shows:

- the generated Rust enums, and the `cents` domain passed as `i32`;
- two dish lists decoded into the same struct (`DishCardRow`);
- the menu read as a stream;
- a customer whose `citext` email ignores case;
- an order inside a transaction;
- the loyalty trigger crediting points when the order is served, and the
  trace of its run.
