With a declarative project, `schema/` describes the database as it should
be — complete `CREATE TABLE`s, functions, triggers, views — and the
migrations are its history, generated from it.

```toml
# pgzest.toml
[schema]
directory = "schema"
declarative = true

[migrations]
directory = "migrations"
```

The analysis and the editor then use the schema; the migrations are
replayed separately and compared with it. As long as they do not reach it,
the latest migration carries a `schema-drift` diagnostic.

## Generating a migration

```sh
pgzest migrate create add_loyalty      # writes the migration, verified by replay
pgzest migrate check                   # CI: fails if the schema moved on alone
pgzest migrate diff old.sql new.sql    # between two schemas, no project
```

`migrate create` compares the state the migrations reach with the schema,
object by object — schemas, extensions, enums, domains, types, sequences,
tables, columns, constraints, views, routines, indexes, triggers,
policies, row-level security, comments — and writes the migration in the
directory's layout: numbered files, Prisma
(`<timestamp>_<name>/migration.sql`) or Diesel
(`<timestamp>_<name>/up.sql`).

```sql
-- pgzest: postgres=18 extensions=citext@1.8,pg_trgm@1.6
-- Migration "search", generated by `pgzest migrate create`.

CREATE EXTENSION IF NOT EXISTS pg_trgm SCHEMA public VERSION '1.6';

ALTER TABLE customers
  ADD COLUMN loyalty integer DEFAULT 0 NOT NULL;

-- !! M006: index public.customers_name_trgm built without CONCURRENTLY: writes to public.customers blocked during the build
CREATE INDEX customers_name_trgm ON customers USING gin (name gin_trgm_ops);
```

- **Verified before it is written**: the migration is replayed after the
  others, and the result must be exactly the schema.
- **Ordered**: what would block the changes first (policies, triggers,
  views to rebuild), then the creations sorted by dependency, the drops
  last.
- **The simplest migration, adapted by you.** It reaches the schema in
  the simplest way, even when that loses data (a rename becomes a drop
  and an add) or fails on a populated table (a `NOT NULL` column without
  default). Only you know the data: the `!! TO ADAPT` header lists what
  to review, and `migrate check` verifies the final state once adapted.
  pgzest never writes data-migration code.
- **Nothing approximated**: a change pgzest cannot express (an enum
  value removed, a domain changed…) is written as a `TODO`, and
  `migrate check` fails until it is written by hand.
- **Risks** on each statement concerned: `M001` to `M007`, from a
  `NOT NULL` column without default to an index built without
  `CONCURRENTLY` ([list](../../reference/diagnostics/#migration-risks)).

The header records the context the migration was generated in — the
PostgreSQL version, the extensions and their versions, the
[run log level](../observability/) of the routines — and the replay
checks the file against it.

## Applying migrations

```sh
pgzest migrate status  --url postgres://…/myapp   # or DATABASE_URL; exit 1 if some are pending
pgzest migrate apply   --dry-run                  # what would run, nothing applied
pgzest migrate apply
```

`apply` runs the pending migrations in order and records each one in
`_pgzest_migrations` (`[migrations] table`), created in the connection's
current schema: no schema of its own, for hosts that allow only `public`.
Nothing is applied unless every check passes:

- **The migrations replay** without error: a migration pgzest cannot read,
  or that PostgreSQL would reject against the state before it, never
  reaches the database. Neither does one still holding the `TODO` lines
  `migrate create` writes for a change left to write.
- **The registry matches the repository**: an applied migration missing
  from the repository, or edited since (its SHA-256 differs), stops the
  run; so does a pending migration that sorts before an applied one — the
  replay verified the repository's order, the database would receive
  another one (rename it after the last applied one).
- **The server matches the headers**: the project's PostgreSQL major
  version; each extension version a pending migration's header names is
  available; the installed extensions are at the versions the last applied
  migration left them. A header describes the state *after* its migration,
  so one that runs `ALTER EXTENSION … UPDATE` carries the new version.

Then:

- **One transaction per migration**, its registry row written in it: a
  failed migration leaves nothing, and the error gives its line in the
  file.
- **`lock_timeout`** of 5 s per migration (`[migrations] lock_timeout`):
  one waiting for a lock queues every query behind it; better to fail and
  retry.
- **One run at a time**: an advisory lock, so replicas starting together
  apply each migration once.
- **Statements that cannot run in a transaction** (`CREATE INDEX
  CONCURRENTLY`, `VACUUM`) go in a migration of their own, run statement by
  statement; mixed with other statements, the migration is refused before
  anything runs. Its row is written as started first: if it fails, what
  ran stays (an invalid index, for instance), and `pgzest migrate resolve
  <name> --applied` or `--rolled-back` records what you found. `BEGIN` and
  `COMMIT` in a migration are refused: they would end its transaction.
- The SQL runs as written: a migration using pgzest macros is refused
  (write their expansion, `pgzest build`). No down migrations: a rollback
  is a new migration.

An applied migration edited on purpose, after review: `pgzest migrate
resolve <name> --checksum`. `db check` reads the registry to know what
the database received.

Prisma and Diesel layouts are not applied by `apply` yet: apply them with
their tool. pgzest will record them in its own registry, and never write
`_prisma_migrations` or `__diesel_schema_migrations`.

### TLS

The URL's TLS parameters are read as libpq reads them, for every command
that connects (`migrate`, `db check`, `db pack`, `dev`):

| `sslmode` | Encrypted | Server checked |
|---|---|---|
| `disable` | no | — |
| `prefer` (default) | if the server accepts | chain, only if an authority file is there |
| `require` | yes | chain, only if an authority file is there |
| `verify-ca` | yes | chain up to an authority |
| `verify-full` | yes | chain, and the certificate names the host |

The authorities come from `sslrootcert` (a PEM file), otherwise
`~/.postgresql/root.crt` (`%APPDATA%\postgresql\root.crt` on Windows);
`sslrootcert=system` uses the system's store and requires `verify-full`.
`PGSSLMODE` and `PGSSLROOTCERT` apply when the URL says nothing. A managed
PostgreSQL usually gives its authority's certificate:

```sh
pgzest migrate apply --url "postgres://app@db.example.net/myapp?sslmode=verify-full&sslrootcert=ca.pem"
```

`sslmode=allow` and client certificates (`sslcert`, `sslkey`) are not
supported: the connection is refused rather than made otherwise.

## An existing project

Migrations of an existing project are read as they are, in their layout:
a Prisma project plugs in without conversion. To move to a declarative
schema, replay them once and write the result:

```sh
pgzest schema import prisma/migrations --layout prisma --out schema --baseline migrations/0000_baseline.sql
```

The import writes one `<schema>/schema.sql` per PostgreSQL schema and a
baseline migration carrying its header; a replay error stops it (`--force`
writes anyway).

## Hand changes in production

```sh
pgzest db check --url postgres://…/myapp   # or DATABASE_URL
```

Compares a database with what its migrations produce, and reports what
was changed in it by hand — a routine hotfixed in production, an index
added, a trigger dropped. Exits 1 when it differs:

```text
error: the database differs from its 5 migration(s), 3 object(s):
  extra    index orders_note_idx on public.orders: only in the database
  changed  routine order_total(bigint):
        …
      - AS $function$ SELECT coalesce(sum(quantity * unit_price), 0)::bigint …
      + AS $function$ SELECT coalesce(sum(quantity * unit_price), 0)::bigint * 2 …
  missing  trigger orders_touch on public.orders: in the migrations, not in the database
```

- The migrations compared are those the database received, as its
  migration tool recorded them (`_prisma_migrations`,
  `__diesel_schema_migrations`); the others are reported as not applied
  yet, and a recorded one the repository lacks is an error. Without a
  migrations table: all of them, or up to `--until <name>`.
- They are replayed in an empty database created on the same server and
  dropped afterwards (the `CREATEDB` privilege), or on another server of
  the same PostgreSQL version with `--scratch-url`.
- Both databases are described by PostgreSQL itself
  (`pg_get_functiondef`, `pg_get_triggerdef`, `format_type`…): a
  difference is one PostgreSQL sees. Column order and the names of
  `NOT NULL` constraints are not compared.
